# 证伪与证据

## 为什么先证伪

模型审查的噪声主要来自「看起来像问题」。每条候选结论先尝试推翻自己：能不能找到一个反例、一个已有处理、一个测试覆盖、一个项目约定？推翻不了，再决定报。报告的强度必须与做过的证据动作匹配。

## 闸门表

| 结论类型 | 必须回答 | 答不上来怎么办 |
|---|---|---|
| 设计不合理 | 可预测场景是什么？现有机制在哪个文件？组合后差在哪一点？ | 降为「待确认」，写明缺什么证据 |
| 宣称与实现不符 | 宣称是什么？实际只做到什么？按宣称使用会在哪一步得到不符预期的结果？ | 放「需要拍板」，不要删 |
| 缺参数/缺省有歧义 | 哪个现有或可预测的调用方会因此传错或绕开？ | 删 |
| 实现 bug | 输入/状态 → 走到哪行 → 得到什么错误结果？ | 降级或删 |
| 并发问题 | 两个执行体在哪个窗口交错？共享对象是什么？可见结果是什么？ | 降为「待确认」 |
| 硬编码 | 它是协议固定值还是业务政策值？若是业务政策值：它必须随什么业务口径变化？不改会怎样静默过期？ | 协议固定值 → 删；业务政策值且说不清随什么变化 → 删 |
| 重复 | 两处符号是什么？哪条需求变化时它们必须一起改？ | 降为 P3 提示或删 |
| 文档不清 | 读者会因此做错什么？ | 删 |
| 过度设计 | 删掉它，今天的损失是什么？ | 删 |
| 既有问题 | 用 `git blame` 或 base 对比确认过吗？它与本次改动无关，还是被本次依赖/放大？ | 与本次无关 → 不报；有关 → 标 `[既有]`，降为 P2 或放「需要拍板」，不进 P0/P1 |
| 安全问题 | 攻击者控制哪个输入？经过哪里？到达哪个 sink？ | 降为「需确认」 |
| 兼容性问题 | 哪个旧调用方、旧数据或旧配置会坏？ | 降级 |

## 证据阶梯

从低到高，结论强度要匹配做过的动作：

1. 只读了 diff → 只能报局部、自洽的问题（明显漏判空、拼写、注释与代码矛盾）。
2. 读了完整函数 + 相邻实现 → 可以报实现缺陷，但要标注未验证调用方。
3. grep 了全部调用方 → 可以报跨组件影响和「缺参数」。
4. 读了测试并确认覆盖/未覆盖 → 可以断言「该分支无保护」。
5. 跑了测试或构造了最小复现 → 可以断言「会这样错」。
6. 读了 git 历史 → 可以区分回归与既有问题。

报告里用一句话交代证据到哪一级，例如「静态阅读 + 全部 7 个调用点」「未运行测试」。

## 每个维度的必答句

- 设计：可预测场景是 ___；现有机制在 ___；组合后差在 ___。
- 缺参数：调用方 ___ 会因此 ___。
- 实现：输入 ___ → 执行到 ___ → 得到 ___（期望 ___）。
- 并发：执行体 A 在 ___ 与 B 在 ___ 交错；共享对象是 ___；结果是 ___。
- 硬编码：它是协议固定值还是业务政策值？若业务政策值：必须随 ___ 变化；不改时会 ___。
- 重复：符号 ___ 与 ___；需求 ___ 变化时两处必须一起改。
- 文档：读者会因此 ___。
- 过度设计：删掉后今天损失 ___（答不上来即成立）。
- 安全：攻击者控制 ___ → 经过 ___ → 到达 ___。

## 常见误判

- **既有问题当回归**：先用 `git blame` 或 base 对比确认归属。确认是既有的：与本次无关 → 不报；被本次依赖或放大 → 标 `[既有]` 并降级，不计入 P0/P1。确认不了归属 → 标「需确认」，不要凭印象归类。
- **把设计后果当缺陷**：先问「这是不是既有设计推导出来的」。是 → 放「需要拍板」，不要写成 bug。
- **把结构性限制吞掉**：如果改动宣称「复现 / 全量 / 只读 / dry-run」，而实现只做到一部分，即使没有崩溃路径，也要作为待拍板项写明差距。判断标准是「按宣称使用会不会得到不符预期的结果」，不是「有没有异常」。
- **把缺失当失败**：可预期的跳过/缺省是正常语义；只有它与失败不可区分、或静默改变汇聚语义时才报。
- **把「我没找到」当「不存在」**：动态派发、DI、反射、跨仓库时，明确标注不确定。
- **把重复当坏味道**：形似但变更理由不同，不算重复。
- **把公开 API 当死代码**：先确认导出面和外部契约。
- **把建议当缺陷**：修法比问题更复杂时，反思问题是否成立，或是否其实是设计问题。
- **把测试风格当缺陷**：除非测试断言了错误行为或会让回归静默通过。

## 报告前自检

- 同一根因是否报了两次？
- 每条是否都有触发路径和证据？
- 是否混入了风格偏好？
- 是否把「需确认」写成了断言？
- 修法是否是最小方向，而不是重写方案？
- 有没有为了凑数把 P3 写成 P1？
- 维度覆盖表里写的「查了什么」，是否真的查过？
- 「已查过没问题」里的每一项，是否真的验证过？有没有把「看起来应该没问题」写成「没问题」？
- 「已查过没问题」里的每一项，**是否都写得出验证方式**（跑了什么 / 读了什么 / 对比了哪个 base）？写不出的删掉——这一段是条件段，没有验证方式的条目比没有这一段更伤信任。
