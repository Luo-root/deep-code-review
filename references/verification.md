# 证伪与证据

## 为什么先证伪

模型审查的噪声主要来自「看起来像问题」。每条候选结论先尝试推翻自己：能不能找到一个反例、一个已有处理、一个测试覆盖、一个项目约定？推翻不了，再决定报。报告的强度必须与做过的证据动作匹配。

## 闸门表

| 结论类型 | 必须回答 | 答不上来怎么办 |
|---|---|---|
| 设计不合理 | 可预测场景是什么？现有机制在哪个文件？组合后差在哪一点？ | 降为 P2，标「需确认：X」，写明缺什么证据；是既有设计推导出来的 → 放「需要拍板」，不要写成 bug |
| 宣称与实现不符 | 宣称是什么？实际只做到什么？按宣称使用会在哪一步得到不符预期的结果？ | **先判是不是设计使然**：是 → 放「需要拍板」，不要删；不是 → 按实际后果定级（文档维见 `dimensions.md` 第 4 维，可能是 P0/P1） |
| 缺参数/缺省有歧义 | 哪个现有或可预测的调用方会因此传错或绕开？ | 删（**仅限「缺参数/缺省」**；错误语义、零值可用性、单位一致性等按第 3 维「实现 bug」判据走） |
| 实现 bug | 输入/状态 → 走到哪行 → 得到什么错误结果？ | 降级或删 |
| 规模与复杂度 | N 的实际取值范围是什么？这条路径随 N 怎么长？实测开销是多少？ | 拿不出规模关系 + 实测 → 删；说不出 N 的取值 → 降为 P2，标「需确认：X」 |
| 并发问题 | 两个执行体在哪个窗口交错？共享对象是什么？可见结果是什么？ | 降为 P2，标「需确认：X」 |
| 硬编码 | 它是协议固定值还是业务政策值？若是业务政策值：它必须随什么业务口径变化？不改会怎样静默过期？ | 协议固定值 → 删；业务政策值且说不清随什么变化 → 删 |
| 重复（真重复） | 两处符号是什么？哪条需求变化时它们必须一起改？ | 答不上来 → **删**；答否（只是形似、变更理由不同）→ **不报**（判据见 `dimensions.md` 第 6 维） |
| 语义分裂 | 两条路径各是什么？**同一个具体输入**下，两条路径的结果差在哪？调用方凭什么知道该走哪条？ | 差不出具体结果差异 → 删；上层注释已承认差异 → 放「需要拍板」 |
| 跨层形状 | 抽象层声明的 ___ 与实现层实际的 ___ 差在哪？换后端要不要连带改调用方代码？ | 答不出两个具体签名 → 删；上层注释已承认差异 → 放「需要拍板」 |
| 职责重叠 | 两个抽象各认领了哪一段职责？边界说不清的话，谁会因为接错方法而写错？ | 说不出谁会因此写错 → 删；边界确实说不清 → 降为 P2，标「需确认：X」；上层注释或设计文档已写明两个抽象各管哪一段 → 放「需要拍板」 |
| 文档不清 | 读者会因此做错什么？ | 删 |
| 过度设计 | 删掉它，今天的损失是什么？ | 答不出具体损失 → **该维成立，按成立条件报**（判据见必答句与 `dimensions.md` 第 7 维）；损失只是「以后可能要加」也算成立 |
| 既有问题 | 用 `git blame` 或 base 对比确认过吗？它与本次改动无关，还是被本次依赖/放大？ | 与本次无关 → 不报；有关 → 标 `[既有]`，降为 P2 或放「需要拍板」，不进 P0/P1 |
| 安全问题 | 攻击者控制哪个输入？经过哪里？到达哪个 sink？ | 降为 P2，标「需确认：X」 |
| 兼容性问题 | 哪个旧调用方、旧数据或旧配置会坏？ | 降级；答不上来 → 降为 P2，标「需确认：X」；若是「旧契约改用哪一种」这类需人来定的兼容性决策 → 放「需要拍板」，不降为 P2 |
| 错误路径与部分失败 | 失败后留下什么半完成状态？能安全重试吗？重试幂等吗？谁负责回滚？ | 说不出具体的半完成状态 → 删；零写入 / 全部分片失败却报成功 → 按「可观测性」行的「成功与失败能不能区分」判，不按半完成状态删 |
| 可观测性 | 排障时会因为看不到哪条信息而查不出问题？成功与失败能不能区分？ | 说不出具体查不出的信息 → 删 |
| 性能 | 调用频率是多少？规模或频率的证据是什么？ | 拿不出规模或调用频率证据 → 删；只是「这里可能慢」 → 删 |
| 测试盲区 | 哪个分支完全没有覆盖？它高风险吗？既有测试会不会静默失效？ | 只是泛泛的「应该加测试」 → 删 |

## 证据阶梯

从低到高，结论强度要匹配做过的动作：

1. 只读了 diff → 只能报局部、自洽的问题（明显漏判空、拼写、注释与代码矛盾）。
2. 读了完整函数 + 相邻实现 → 可以报实现缺陷，但要标注未验证调用方。
3. grep 了全部调用方 → 可以报跨组件影响和「缺参数」。
4. 读了测试并确认覆盖/未覆盖 → 可以断言「该分支无保护」。
5. 跑了测试或构造了最小复现 → 可以断言「会这样错」。
6. 读了 git 历史 → 可以区分回归与既有问题。

报告里用一句话交代证据到哪一级，例如「静态阅读 + 全部 7 个调用点」「未运行测试」。

**没有基线时**（模块体检、目录审查、函数级审查）没有 diff 可读，**从第 2 级起**——「读了完整函数 + 相邻实现」是最低档，其余各级不变。

## 每个维度的必答句

> 必答项以闸门表的「必须回答」列为准——本节是它的速查副本，不是独立判据。发现两处不一致时以闸门表为准，并按 `SKILL.md` 的「同一判据写两份必然漂移」修这一份。

- 设计：可预测场景是 ___；现有机制在 ___；组合后差在 ___。
- 缺参数：调用方 ___ 会因此 ___。
- 跨层形状：抽象层声明的 ___ 与实现层实际的 ___ 是同一个形状吗；差在哪（字段类型 / 字段数量 / 返回类型 / 参数打包方式）？换后端要不要连带改调用方代码？
- 实现：输入 ___ → 执行到 ___ → 得到 ___（期望 ___）。
- 规模：N 的取值范围是 ___；这条路径随 N 怎么长（___）；实测开销是 ___。
- 并发：执行体 A 在 ___ 与 B 在 ___ 交错；共享对象是 ___；结果是 ___。
- 硬编码：它是协议固定值还是业务政策值？若业务政策值：必须随 ___ 变化；不改时会 ___。
- 重复：符号 ___ 与 ___；需求 ___ 变化时两处必须一起改。
- 语义分裂：路径 ___ 与 ___；同一个输入 ___ 时，两条路径分别得到 ___ 与 ___；调用方凭什么知道该走哪条？
- 职责重叠：抽象 ___ 认领 ___，抽象 ___ 认领 ___；边界不清会让 ___ 写错 ___。
- 文档：读者会因此 ___。
- 过度设计：删掉后今天损失 ___（答不上来即成立）。
- 安全：攻击者控制 ___ → 经过 ___ → 到达 ___。
- 兼容性：旧调用方 / 旧数据 / 旧配置是 ___；它会坏在 ___。
- 错误路径与部分失败：失败后留下 ___；能重试吗（___）；谁回滚 ___。
- 可观测性：排障查不出的是 ___；成功与失败能不能区分（___）。
- 性能：调用频率 ___；规模或频率的证据是 ___。
- 测试盲区：没覆盖的分支是 ___；它高风险吗（___）。

## 常见误判

- **既有问题当回归**：先用 `git blame` 或 base 对比确认归属。确认是既有的：与本次无关 → 不报；被本次依赖或放大 → 标 `[既有]` 并降级，不计入 P0/P1。确认不了归属 → 标「需确认」，不要凭印象归类。
- **把设计后果当缺陷**：先问「这是不是既有设计推导出来的」。是 → 放「需要拍板」，不要写成 bug。
- **把结构性限制吞掉**：如果改动宣称「复现 / 全量 / 只读 / dry-run」，而实现只做到一部分，即使没有崩溃路径，也要作为待拍板项写明差距。判断标准是「按宣称使用会不会得到不符预期的结果」，不是「有没有异常」。
- **把缺失当失败**：可预期的跳过/缺省是正常语义；只有它与失败不可区分、或静默改变汇聚语义时才报。
- **把「我没找到」当「不存在」**：动态派发、DI、反射、跨仓库时，明确标注不确定。
- **把重复当坏味道**：形似但变更理由不同，不算重复。
- **把语义分裂当真重复**：单源测试答「是」，但两条路径在同一输入上结果不同 → 按**语义分裂**走（tie-break 见 `dimensions.md` 第 6 维）。反过来，两条路径各自自洽、只是名字像同一个东西 → 不算语义分裂。
- **把公开 API 当死代码**：先确认导出面和外部契约。
- **把建议当缺陷**：修法比问题更复杂时，反思问题是否成立，或是否其实是设计问题。
- **把测试风格当缺陷**：除非测试断言了错误行为或会让回归静默通过。

## 报告前自检

- 同一根因是否报了两次？
- 每条是否都有触发路径和证据？
- 是否混入了风格偏好？
- 是否把「需确认」写成了断言？
- 修法是否是最小方向，而不是重写方案？
- 有没有为了凑数把 P3 写成 P1？
- 维度覆盖表里写的「查了什么」，是否真的查过？
- 「已查过没问题」里的每一项，是否真的验证过？有没有把「看起来应该没问题」写成「没问题」？
- 「已查过没问题」里的每一项，**是否都写得出验证方式**（跑了什么 / 读了什么 / 对比了哪个 base）？写不出的删掉——这一段是条件段，没有验证方式的条目比没有这一段更伤信任。**准入门槛以 `SKILL.md` 与 `references/output-template.md` 的表述为准**：跑了测试、构造了复现、对比了 base，或对某个高风险面做了专门证伪，四者之一。
