## 必须修

### [P1][实现] internal/ratelimit/redis.go:88 — Redis 超时后放行全部请求
- 触发：`redis.Do` 返回 `context.DeadlineExceeded`
- 影响：限流形同虚设，故障期间全部流量打满下游
- 证据：`:91` 把错误当「未限流」返回；`TestRedisError` 只断言不 panic（redis_test.go:40）
- 修法：超时走本地兜底计数器（已有 `localFallback`，:120），不要返回放行

### [P1][方法] internal/ratelimit/limiter.go:33 — `Allow(key string, n int)` 无法表达「只扣一次」
- 触发：批量接口按请求数调用 `Allow(key, len(items))`，重试时会重复扣减
- 影响：一次重试把配额扣两次，用户被提前限流
- 证据：`handler/batch.go:71` 在重试外层循环里调用；同文件 `:80` 又手工回补一次，说明契约不够
- 修法：拆成 `Check(key)` 与 `Consume(key, n)`，或让 `Allow` 接受幂等键

- 建议：A。仓库里 3 个调用方都经过 middleware，`KeyFunc` 能覆盖且不新增装配代码。
- 要你定：租户 id 是否已经在 handler 上下文里可取；如果取不到，选 B。

## 语气与排版

- 结论先行，不铺垫、不寒暄、不复述 diff。
- 一条 finding 一段，不写「此外」「值得注意的是」。
- 用大白话解释机制；需要精确时才引入术语。
- 设计取舍给最小对照例子（「A 情况下会怎样，B 情况下会怎样」），不要只给判断。
- 行号只用于定位；论据是调用方、数据流、测试结果。
- 不确定的写「需确认：___」，不要用「可能」「也许」堆在确定结论里。
