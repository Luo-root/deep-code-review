覆盖表的「结果」格用**三态**：`无发现` / `未扫（理由）` / `n 条`。扩展维度**各自成行**，不要合并——合并之后「无」就分不清是「扫了没问题」还是「压根没扫」。

「已查过没问题」是**条件段**：只有真的跑了测试、构造了复现、或对某个高风险面做了专门证伪时才写；否则整段省略，并在「本次没覆盖」里写明未做验证。写了就每条带一句验证方式。

## 零发现模式（不要套六段）

没有任何 P2 以上的问题时，不要输出上面的骨架。直接给结论 + 1~2 句说明：

```markdown
## 结论

范围：`feature/rate-limit` 相对 `main` 的 2 个文件（merge-base `a1b2c3d`）。
结论：**可以合** —— 没有发现 P2 以上的问题。

查了什么：完整读了 2 个改动文件与全部 5 个调用点；核对了参数绑定形式与退出码。
未覆盖：未运行测试，结论基于静态阅读。
```

## 语气与排版

- 结论先行，不铺垫、不寒暄、不复述 diff。
- 一条 finding 一段，不写「此外」「值得注意的是」。
- 用大白话解释机制；需要精确时才引入术语。
- 设计取舍给最小对照例子（「A 情况下会怎样，B 情况下会怎样」），不要只给判断。
- 行号只用于定位；论据是调用方、数据流、测试结果。
- 不确定的写「需确认：___」，不要用「可能」「也许」堆在确定结论里。
- 零发现时不要为了凑满六段而写空表、空标题。
