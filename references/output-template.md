# 输出模板

finding 的**字段定义**以 `SKILL.md` 的「输出契约」一节为准，本文件只给骨架与示例。

覆盖表的「结果」格用**五种取值**：`无发现` / `已查（见 X）` / `未扫（理由）` / `n 条（级别）` / `n 条（级别），另见 X`；`n>0` 时**必须**带级别标注（`2 条（P1）`、`1 条（待拍板）`）——不带级别就和结论行对不上账，n=0 写「无发现」。**一个维度同时有多个级别时写「n 条（P2 1、待拍板 1）」**——各级各占一个数量，与结论行逐级对账。第 5 种用于本维既有自己的条目、又有结论归到别的维度时。`已查（见 X）` 只在结论归到了别的维度时用，**且只出现在结果格**——「查了什么」列不要用它；那一列每行至少给一个可核对的事实（文件/行号、函数名、grep 到的数量、读过的测试名，或「未跑测试」）。扩展维度**各自成行**，不要合并——合并之后「无」就分不清是「扫了没问题」还是「压根没扫」。

**范围行按基线类型分形态**（分支 / PR、commit 级、工作区改动、无基线各一种）——**格式以 `SKILL.md` 输出契约的「范围行按基线类型分形态」那张表为准**，本文件不复述。骨架里示范的是**分支 / PR** 那一支；审 commit 级或工作区改动时按那张表换形态，不要把 merge-base 硬套上去。

**无基线时**（模块体检、目录审查），范围行写「范围：`<路径>`（无基线，全量体检）」——不要编一个 merge-base 出来。**意图来源全都没有时**（无基线体检最常见：没有 PR 正文、没有 commit message 可读），结论段再加一行「意图：<你理解的这份代码要做什么>」——意图只能靠推断，说出来作者才能纠正。**有基线但读不到 PR 正文 / commit message** 时同样要写这一行。

**无基线时 finding 标签的第三段写 `[现状]`**（三段形态不变）：`### [P2][文档][现状] internal/checkout/service.go:30 — ...`。第三段的合法取值只有 `本次引入` / `既有` / `现状`；`[既有]` 出现在无基线报告里就是错的——那等于宣称有一个不存在的基线。

「已查过没问题」是**条件段**：只有真的跑了测试、构造了复现、**对比了 base**，或对某个高风险面做了专门证伪时才写；否则整段省略，并在「本次没覆盖」里写明未做验证。写了就每条带一句验证方式（跑了什么 / 读了什么 / 对比了哪个 base）。

## 零发现模式（不要套七段）

没有 P0–P2、也没有待拍板项时，不要输出上面的骨架。给结论 + **「宣称：… ／ 实际：…」那一行** + **维度覆盖表（15 行，每行都要有结论）** + 1~2 句说明。**结论行仍写各级数量**（没有 P0–P2 时写 `P0 0、P1 0、P2 0、P3 n、待拍板 0`）。只有 P3 时同样一句话收尾，把 P3 列成「可选改进」条目（**每条 P3 一项；P3 达两条及以上时改用七段骨架的「建议修」段**），字段仍按建议修的四行（问题 / 证据 / 收益 / 修法）——不为一条 P3 展开整份骨架，但也不把它丢掉。

**覆盖表在零发现时也要写**：它正是「我扫过了」与「压根没扫」的区分——「可以合」可信，靠的就是这 15 行。

```markdown
## 结论

范围：`feature/rate-limit` 相对 `main` 的 2 个文件（merge-base `a1b2c3d`）。
结论：**可以合** —— P0 0、P1 0、P2 0、P3 0、待拍板 0。
宣称与实际一致。

## 维度覆盖

| 维度 | 结果 | 查了什么 |
|---|---|---|
| 设计 | 无发现 | middleware 链、option 结构、3 个调用方 |
| 方法契约 | 无发现 | 4 个导出函数的参数与默认值 |
| ……（15 行，每行都要有结论） | | |

查了什么：完整读了 2 个改动文件与全部 5 个调用点；核对了参数绑定形式与退出码。

```

## 快模式输出（回归判定）

紧凑列表，每条 = 标题 + 3 行正文（触发 / 影响 / 修法），不带覆盖表；P2/P3/「需确认」用「问题 / 证据 / 收益 / 修法」4 行，待拍板用「现状 / 证据 / 路线 A / 路线 B / 建议 / 要你定」。

**开头三行**：范围与基线 → 结论 → 各级数量；**读不到意图来源时**加一行「意图：…」。**再一行**：「宣称：… ／ 实际：…」（两档同一条句式）。**结尾一行**：未覆盖的部分（没跑测试、抽样比例、跳过的分支），固定写成「未覆盖：<…>」——抽样时必写抽样比例。

```markdown
范围：`feature/rate-limit` 相对 `main` 的 2 个文件（merge-base `a1b2c3d`）。
**改完再合** —— P0 0、P1 1、P2 0、P3 0、待拍板 0。
意图：让限流器在 Redis 不可用时降级为本地计数，而不是全量放行。
宣称：Redis 超时时降级为本地计数 ／ 实际：Redis 超时时把错误当成「未限流」，放行全部请求。

- [P1][实现][本次引入] `internal/ratelimit/redis.go:88` — Redis 超时后放行全部请求
  触发：`redis.Do` 返回 `context.DeadlineExceeded`，`:91` 把错误当「未限流」返回。
  影响：限流形同虚设，故障期间全部流量打满下游。
  修法：超时走本地兜底计数器（已有 `localFallback`，`:120`）。

未覆盖：未运行测试，结论基于静态阅读 + 全部 5 个调用点。
```

## 语气与排版

- 结论先行，不铺垫、不寒暄、不复述 diff。
- 一条 finding 一段，不写「此外」「值得注意的是」。
- 用大白话解释机制；需要精确时才引入术语。
- 设计取舍给最小对照例子（「A 情况下会怎样，B 情况下会怎样」），不要只给判断。
- 行号只用于定位；论据是调用方、数据流、测试结果。
- 不确定的写「需确认：___」，不要用「可能」「也许」堆在确定结论里。
- 零发现时不要为了凑满七段而写空段、空标题——但**覆盖表要写满 15 行**，每行都要有结论。
