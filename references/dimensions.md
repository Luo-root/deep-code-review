# 七维扫描细则

每个维度给出：核心问题、扫描动作、成立条件、常见误报。扫描动作是提示清单，不是逐条打卡；按改动性质挑相关的做，没做的不算「查过」。

本文件的「成立条件」与「不算」是**细则**，`SKILL.md` 的七维表是速查；两者措辞不一致时以本文件为准。

## 1. 设计：现有机制能否自然组合

**核心问题**：这次改动要的能力，现有机制组合能不能给？新增的抽象是不是在替组合做决定？

**扫描动作**

1. 先列出项目已有的扩展面：中间件/切面/拦截器、option 结构、钩子、注册表、插件、事件、策略接口、泛型、已有工具函数、配置层。
2. 列出改动新增的公开类型、函数、配置项、参数，逐个问：`现有 A + B` 能不能达到同样效果？
3. 反向问：这段新代码是否重新实现了上面某个机制（与第 6 维合看）。
4. 看调用方：新机制是否要求每个调用方手写同样的装配/样板？本该由组合层一次完成的事散给调用方，就是把出错机会复制 N 份。
5. 对新 API 追问一句「开发者在哪容易写错」：如果它只是把编译器本来就能查的东西再锁一遍（更多类型参数、更多专用重载），却没消灭任何一类具体写错，按过度设计处理。

**成立条件**

- 能给出一个可预测场景（「再加一个同类后端」「同一能力要在另一条路径复用」「调用方从 1 个变 3 个」），并指出组合点在哪个文件。
- 两种情况都算：现有机制够用（新增抽象多余）；现有机制只差一点（该补组合点而不是给每个调用方加特例）。

**不算**

- 只是「我会换一种写法」。
- 新抽象已经有第二个真实使用者（仓库内能指出来）。
- 为了隔离外部依赖而多一层接口，且这个依赖在测试里确实被替换。

**写法**

> 新增的 `WithRetry(n)` 和现有 `RetryMiddleware` 能力重叠：后者已支持指数退避和超时（middleware/retry.go:31），前者只有固定间隔。仓库里两个消费者都在用中间件，给中间件补一个 `WithBackoff` 参数即可，不必新增入口。

## 2. 方法契约：参数遗漏与缺省歧义

**核心问题**：真实调用中，调用方会不会传错、漏传，或者为了达到目的绕过这个函数自己拼？

**扫描动作**

1. 对每个新/改的导出函数，列出它需要的全部信息，逐个问「从哪来」：参数？配置？全局？调用方二次计算？要调用方重复计算，通常就是不该由它承担的。
2. 可选参数：零值是否同时表示「没传」和「传了零值」？空字符串、0、nil 指针、空切片能不能区分？需要区分的场合，缺的是指针、`Option`，还是显式三态。
3. 缺省值：写在文档里，还是藏在实现里？默认值是否会随环境悄悄不同？
4. 长链路：是否缺 `ctx`；是否在内部把 `ctx` 换成 `Background`；超时/取消能不能传到最底层。
5. 失败：错误能不能被调用方感知？是否用「返回零值 + 打日志」代替 error？
6. 限制类：批量大小、并发度、超时、重试、缓冲区是否有入口？默认值是否锁死（接第 5 维）。
7. 同型相邻参数：`func(a, b string)` 在调用处能否一眼看出哪个是哪个？两个 string/bool 相邻且语义不同，是高频写错点。
8. 变体缺失：现有调用方是否在函数外面自己拼装、自己重试、自己过滤？这说明函数少了一个参数或一个变体。
9. 校验：非法参数是入口早失败，还是走到深处才炸、甚至静默算错？

**成立条件**：指出至少一个现有调用方（或明确可预测的调用方）会因此写错。

**不算**：参数多但每个都有明确语义和文档；用 option 结构承载可选参数是正常做法。

**写法**

> `NewShardReader(path string, shardID int)` 没有 `ctx`，但内部 `open` 带 10s 超时（shard.go:88）；上层取消后这里仍要等满 10s。加 `ctx` 参数，或让调用方传入的 ctx 贯穿到 `open`。

## 3. 实现缺陷

**核心问题**：在什么具体输入或执行交错下，行为会与预期不符？

**扫描动作**

- 边界：空、0、负数、单元素、超长、重复项、未排序、空字符串、多字节/代理对、时区边界。
- 分支：早返回是否漏清理；switch 是否有 default；错误分支是否吞掉；`err` 是否被后续赋值覆盖。
- 部分失败：写了一半、发了一半、删了一半之后失败，留下什么状态？能不能重试？重试是否幂等？谁负责回滚？
- 并发：共享 map/slice/字段是否有保护；channel 由谁关闭、关闭后还会不会发；每个 goroutine 是否有退出路径；取消后是否还在跑。
- 资源：file/conn/lock/timer 是否释放；defer 是否在循环里堆积；缓存是否有上限和淘汰。
- 数值：整型溢出；除法取整方向；秒/毫秒混用；浮点比较。
- 时间语义：把 `now` 换成历史基准、换时区、换单位后，每个时间窗口是否仍有上下界？排序方向是否仍成立？「最近 N 小时」这类相对文案是否仍准确？（只改时钟不改查询上界，会把「未来数据」纳入历史结果。）审计/变更/日志时间戳（常写成 `Instant.now()`）是否也走同一基准？
- 顺序与别名：map 遍历顺序是否影响结果；切片/缓冲区是否被共享后意外改写；append 是否复用底层数组。
- 错误值：是否用字符串比较判错；`%w` 是否丢失；sentinel error 被包装后是否还在用 `==` 比较。

**成立条件**：给出「输入/状态 → 具体行 → 错误结果」。没有可达路径的理论问题降级。

**不算**：框架/运行时已经保证的前提（例如单测里没有并发）；已有测试覆盖且断言正确的路径。

## 4. 文档

**核心问题**：读者照文档做，会不会做错？

**扫描动作**

- 公开符号注释是否说明：何时用、副作用、并发安全、错误语义、单位、零值含义。
- 注释是否与代码漂移：参数改名、默认值改了、示例编译不过。
- 错误信息是否给出下一步（`field x must be > 0, got -1` vs `invalid input`）。
- README/设计文档的承诺 vs 实现（「幂等」「至少一次」「线程安全」）。
- 同一概念是否两个名字；旧名字是否还残留。
- 破坏性变更是否有迁移说明。

**成立条件**：指出读者会因此做错什么（传错、以为幂等、以为线程安全、照着示例编译失败）。

**不算**：只是啰嗦、错别字、纯排版。

## 5. 硬编码

**核心问题**：哪个值本该可变，却被写死了？

**扫描动作**

- 数字：超时、重试、缓冲、页大小、端口、并发度、阈值、批量大小。
- 字符串：URL、host、路径、topic、表名、header、错误码、租户/环境/分支名、镜像 tag。
- 平台假设：路径分隔符、时区、locale、大小写敏感、行尾。
- 版本/地址：版本号、commit、IP、证书路径。
- 测试数据/测试账号进入生产路径。
- 永远为真的开关（feature flag 写死 true）或永远走不到的分支。

**判断分两档**

- **算**：它必须随环境/租户/调用方/数据规模/版本变化；或它会随外部世界变化而静默过期（证书、URL、表结构）。
- **不算**：真不变量（协议固定值、7 天），已命名、已注释、只有一个使用者。

**修法按「需要变化的边界」选最小一档**：命名常量 < 函数参数 < 配置项 < 运行时发现。不要一律上配置。

## 6. 重复

**核心问题**：同一行为是否存在第二个真相源？

**扫描动作**

- 近名函数多处实现同一逻辑：retry、parse、validate、format、hash、默认值、错误包装。
- 复制后已漂移：一边修了 bug，另一边没修。
- 同一常量/正则/错误文本在多处字面量重复。
- 两套并行抽象做同一件事（两套 errors、两套 config、两套 client、两套日志）。
- 测试里复制了实现逻辑，导致没测到真实现。
- 同一段编排在多个 handler 里重复（往往是缺一个组合点，接第 1 维）。

**成立条件（单源测试）**：「哪条需求变了，这两处必须一起改？」回答是 → 真重复；回答否 → 形似，不报。

**修法不一定是抽公共函数**：可能是删掉一份、让一方调用另一方、把差异参数化。报告里要指明哪一份是真相源。

## 7. 过度设计

**核心问题**：删掉它，今天会损失什么？

**扫描动作**

- 只有一个实现、且没有第二个使用者的接口/抽象。
- 仓库内无调用、导出面也无人使用的公开 API（先确认不是对外契约）。
- 为「未来可能」准备的配置项、参数、开关、钩子。
- 只做透传的层（A→B→C，中间层没有逻辑）。
- 为不可能状态写的防御代码。
- 通用化到 N 个维度、实际只用 1 个。
- 抽象成本大于内联：读它要跳 5 个文件。
- 为性能牺牲可读性，但没有基准或规模证据。

**成立条件**：答不出「删掉它今天的损失」，或损失只是「以后可能要加」。

**不算**：公开 API/插件接口（对外契约，内部无调用正常）；已有第二个使用者；防御的是真实外部输入。

**与第 1 维的分工**：第 1 维问「这个能力该不该用现有机制组合」，第 7 维问「这个机制本身是不是多余」。

## 扩展维度

### 错误路径与部分失败

失败后留下什么状态？能否安全重试？重试是否幂等？多步操作的中间态对读者是否可见？回滚由谁负责？只报能指出具体半完成状态的情况。

> 批处理/Job 类改动里，本节大部分已由 `playbooks.md` 的「批处理 / Job / CLI」覆盖（成功判定、游标、幂等）。命中该 playbook 时**以 playbook 为准，不要重复扫**；覆盖表里写「已查（见批处理 playbook）」。

### 并发与生命周期

锁的粒度与顺序（死锁）；共享可变状态；channel 的关闭权与发送方；goroutine 退出；ctx 取消传播；定时器/监听器是否泄漏。结论必须能说出两个执行体的交错窗口。

> 「并发 / 服务 / 守护进程」playbook 覆盖了本节绝大部分，并额外查启动/关闭顺序与重试放大。命中该 playbook 时**以 playbook 为准，不要重复扫**。

### 安全

用户可控输入到 sink 的路径：SQL/命令/模板注入、路径穿越、越权（缺 tenant/owner 校验）、SSRF、反序列化、密钥或 token 进日志、默认允许。只报有具体入口的。

### 兼容性

公开 API、DB schema、配置键、wire format、错误码变更；旧客户端/旧数据/灰度期双写；默认值改变导致的静默行为变化。指出谁会坏。

> 「API / 库 / SDK」playbook 覆盖了默认值、零值歧义与向后兼容。命中该 playbook 时以 playbook 为准，不要重复扫。

### 可观测性

错误被吞、日志缺关键 id（请求/租户/消息 id）、成功与失败无法区分、重试不可见。只在排障会因此变瞎时报告。

> 「配置 / 部署 / 脚本」playbook 额外查退出码、健康检查与告警；批处理 playbook 额外查退出码与摘要文案。

### 性能

N+1 查询、循环内 IO、无界分配/缓存、锁内做慢操作、重复序列化。要有规模或调用频率证据，不做微优化猜测。

### 测试盲区

只报：测试断言了错误行为；改动让既有测试静默失效（例如 mock 了新签名但没验证行为）；关键分支完全没有覆盖且该分支高风险。不报泛化的「应该加测试」。
