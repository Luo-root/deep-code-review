# 快模式：合并判定契约

用户只问「有没有回归」「能不能合」时走这一档。目标是**一句话能回答"能不能合"**，不是把所有能说的都说出来。

## 范围与基线

- 用户给了范围就照他的范围；没给，且「换一种理解会改变结论」时才问。
- 工作区改动：staged + unstaged + untracked，相对 HEAD。
- 分支 / PR：用 merge-base，不用整棵树当 diff。
- 不要把用户明确指定的文件、函数、commit、PR 换成「当前未提交的改动」。
- **要写出来，不只是定下来**：报告开头必须有一行「范围：`<PR/分支/路径>` 相对 `<base>`（merge-base `xxxxxxx`）」。**一个没有作用域的「能不能合」是最容易被误用的结论**——换个 PR 问同样的问题，字面输出一样。
- **快模式必须有基线**：快模式判的是「本次改动有没有坏」，没有基线就没有「本次改动」可言。用户问的是模块体检、目录审查这类**没有基线**的场景时，直接走全量模式（无基线分支见 `SKILL.md` 的坐标系），别在快模式里编一个不存在的「本次改动」。

## 校准

- **只报本次改动引入的缺陷。** 基线之前就存在的问题不作为回归报出——除非它被本次直接放大、或本次功能直接依赖它；那时标 `[既有]` 并说清关系。
- **命中改动类型时，跑命中的那几节 playbook 的必查项**（清单见 `references/playbooks.md`；命中判据是各节顶部的载体表）——它们列的正是「本次引入」的缺陷：批处理的成功判定/游标/幂等、API 库的默认值与向后兼容、配置部署的退出码与密钥。**命中几节跑几节，必查项取并集**（漏一节就等于那一维的覆盖面归零）；**一节都不命中就不跑**，别平铺到每次审查。
- **只报可执行的缺陷。** P0/P1 每条都要能写出「什么输入/状态 → 走哪条路 → 看到什么错误结果」；**规模与性能类例外**：这类结论本来就没有错误结果（见 `references/dimensions.md` 的「规模与复杂度」），触发行改写「N=___ 时实测 ___」，规模关系与实测数字就是它的触发路径；P2/P3 与「需确认」条目的形态见下方「输出」一节（它们没有触发路径，按「问题 / 证据 / 收益 / 修法」写）。
- **验证过调用方再谈跨组件影响。** 没找到调用方时写「需确认」，不把「我没找到」写成「没有调用方」。
- 不报：格式、拼写、lint、命名口味、主观重构偏好、没有具体回归路径的「建议补测试」。
- 不报臆测：无法验证的怀疑删掉，不要靠「可能 / 也许」堆结论。
- 同一根因只报一次，其余受影响的位置列在同一条里。
- 报完所有符合条件的，**不要在第一条发现就停下**。
- 引用的行号范围尽量短。

## 只读

审查是只读的：不改文件、不提交、不推送、不开 PR。除非用户明确要求动手。**「只读」指不改被审仓库**——取证（基准、探针、最小复现）可以在**仓库外的临时副本**里做，被审目录保持原样。**副本要跟被审的是同一份系统**（同一个 commit + 同一份构建输入；带不过去的构建输入就别引用实测数字，判据见 `references/dimensions.md` 的「怎么拿实测数字」）。

## 输出

紧凑列表，一条 = 标题 + 3 行正文（触发 / 影响 / 修法）。**标签形态与全量模式一致**（`[级别][维度][引入方式]`）——快模式只是不套骨架，标签不省、字段也不省：**证据并入「触发」行**（写清读到的位置、是否实测），不单独占行。**P2 / P3 与「需确认」条目没有触发路径，改用「问题 / 证据 / 收益 / 修法」四行**（证据不并入触发行）；待拍板项的形状见下。

**开头三行**：范围与基线 → 结论（可以合 / 改完再合 / 方向先定）→ 各级数量（`P0 n、P1 n、P2 n、P3 n、待拍板 n`；零发现时不写数量）。**有基线但读不到意图来源时**（没有 PR 正文、commit message、关联 issue）加一行「意图：<你理解的这次改动要做什么>」——说法要具体到能被作者纠正，不能是「优化性能」这种空话。

**再一行**：「宣称：<这个改动说它要做到什么> ／ 实际：<代码里实际做到了什么>」。两档同一条句式（写法见 `SKILL.md` 第 1 步），没有落差写「宣称与实际一致」。

**结尾一行**：未覆盖的部分（没跑测试、抽样比例、跳过的分支），固定写成「未覆盖：<…>」。**范围太大只能抽样时必写**（「抽查 12/87 个文件，按风险排序；其余未读」）——不写抽样比例，读者会以为全量看过了。

```markdown
范围：`feature/rate-limit` 相对 `main`（merge-base `a1b2c3d`）。
**改完再合** —— P0 0、P1 1、P2 0、P3 0、待拍板 0。
意图：让限流器在 Redis 不可用时降级为本地计数，而不是全量放行。
宣称：Redis 超时时降级为本地计数 ／ 实际：Redis 超时时把错误当成「未限流」，放行全部请求。

- [P1][实现][本次引入] `internal/ratelimit/redis.go:88` — Redis 超时后放行全部请求
  触发：`redis.Do` 返回 `context.DeadlineExceeded`，`:91` 把错误当「未限流」返回。
  影响：限流形同虚设，故障期间全部流量打满下游。
  修法：超时走本地兜底计数器（已有 `localFallback`，`:120`）。

未覆盖：未运行测试，结论基于静态阅读 + 全部 5 个调用点。
```

**撞见方向性取舍时**（两条路径行为不一致、职责边界说不清这类）：结论档用**「方向先定」**（判据见 `SKILL.md` 的结论档表）——它表示「方向得先定，改哪条 finding 都没意义」。条目仍按快模式的紧凑形态写，但正文要给「现状 / 证据 / 路线 A / 路线 B / 建议 / 要你定」；也可以升级到全量模式按七段写。

**零发现时一句话说完**，不要套七段骨架：

```markdown
范围：`feature/rate-limit` 相对 `main`（merge-base `a1b2c3d`）。
**可以合**。没有发现本次改动引入的缺陷。查了什么：完整读了 2 个改动文件与全部 5 个调用点。
未覆盖：未运行测试，结论基于静态阅读。
```

## 什么时候升级到全量

判据只有一个：**用户在问什么**（见 `SKILL.md` 的「两档模式」）。出现下面任一情况，停下快模式，改走全量（`SKILL.md` 的执行顺序）：

- 用户其实在问设计、契约、重复、过度设计，或要「给这个模块做个体检」；
- 用户同时问了两件事（「能不能合」**和**「设计有没有问题」）；
- 用户明确要覆盖表、维度覆盖，或说「按我的标准审」。

**改动有多大不是升级理由。** 改动跨多个模块、新增了公开 API、发现一个「既有但被本次放大」的问题——这些都**留在快模式**，但要相应加查：跨模块的改动把每个跨模块调用点都 grep 一遍；新增公开 API 就多查它的所有调用方与 godoc；发现被放大的既有问题就标 `[既有]` 并写清关系。**用户问「能不能合」却拿到一份设计体检报告，和拿到一份漏查的报告一样糟。**
