# 按改动类型的追加检查

七维是通用面；下面这些改动类型有高频专属缺陷。先认类型，再追加对应清单——只对命中的类型展开，不要平铺到每次审查。

**扫描顺序**：先认改动类型 → 跑该类型的必查项 → 七维做通用面 → 规模扫描 → 扩展维度只做横向补充。

每份 playbook 开头标注了它覆盖了扩展维度的**哪些条目**。**扫完 playbook 即视为它列出的那些条目已覆盖，不再重复扫**；**同一维度里它没列出的条目，仍要按该维度自己扫**（该维度的条目清单在 `references/dimensions.md` 对应小节）：结果格按 `SKILL.md` 的四种取值写（扫过且干净写「无发现」），覆盖说明写在「查了什么」列（如「由批处理 playbook 覆盖：…」）。

**覆盖声明以每份 playbook 开头的「覆盖扩展维度」那一行为准**——声明与它覆盖的条目摆在同一页，对不上就是漂移（`dimensions.md` 里各扩展维度的覆盖注记只是指针）。**声明必须逐维度写出条目名，不许只写维度名**：只写维度名等于宣称整节覆盖，而该维度的清单里往往还有 playbook 没查的条目——那些条目不会因为声明写了个维度名就自动被扫到。

**每条必查项后面的括号是它归属的规范维度，只有一个**，报出来时直接用它当 finding 标签的维度段（见 `SKILL.md` 的「标签形态固定三段」）。一条必查项同时牵涉两个维度时，拆成两条、每条各标一个。

**规模扫描（`dimensions.md` 的「规模与复杂度」）不被任何 playbook 覆盖**——它跟改动类型无关，只要代码里有循环、递归、聚合、查找或整块拷贝就要跑。下面各类型里带「规模」标记的条目是**该类型的高发场景**，不是规模扫描的替代品：通用扫描跑完之后，再看这一类型有没有额外的规模雷区。

## 批处理 / Job / CLI

覆盖扩展维度：错误路径与部分失败（成功判定、游标 / 断点、幂等）、并发与生命周期（后台进程）、可观测性（退出码与摘要）。

- **成功判定**（错误路径与部分失败）：零写入、全部分片失败、全部跳过，是否仍返回 SUCCESS？「成功」是否等于「至少做成一件」？
- **游标 / 断点**（错误路径与部分失败）：失败是否推进游标？跳过是否推进？重试入口是什么？`--reset` 会不会重复写？
- **幂等**（错误路径与部分失败）：重跑同一输入会追加副本吗？有没有幂等键或批次标记？崩在「数据已写、进度未存」之间会怎样？
- **后台进程**（并发与生命周期）：会不会启动队列消费者、定时任务、HTTP 端口？这些在「单次运行」模式下是否仍被启动？
- **默认目标环境**（硬编码）：默认连的是哪个环境（生产 / 预发 / 本地）？它是业务政策值——换个部署环境要改代码吗（判据见 `dimensions.md` 第 5 维）？
- **目标环境断言**（实现）：有没有挡住「在生产库上跑迁移 / 回填」的断言？跑错环境时的可见结果是什么？
- **dry-run**（实现）：参数是否真的接线？只读是否覆盖所有写路径？启动日志里能否看出 dry-run 生效？
- **参数绑定**（方法契约）：`--key=value` 与 `--key value` 在当前框架里是否等价？裸 flag 是否真的映射到 `@Value` 的 key（`--dry-run` vs `memnet.replay.dry-run` 这种改名最容易断链）？命令行、环境变量、配置文件三个来源的优先级是否清楚？
- **退出码与摘要**（可观测性）：部分完成是否以 0 退出？「完成」文案是否与实际处理量一致？
- **分页**（方法契约）：只处理一页会不会被误认为全量？`limit` 与总量的关系是否可见？
- **规模（该类型高发）**（规模与复杂度）：批处理的数据量是最大的——逐条扫描里有没有嵌套扫描（O(n²)）、有没有把整批结果每轮复制一遍、有没有为每条记录重扫一次声明表？批次的「规模」是多少（一次 1 万条还是 100 万条）？这个数字要能从代码或配置里读出来，不能靠猜。

命中这些项时，每条都要落到具体行；「文档这么写、代码没这么做」本身就是合法结论。

## 数据重放 / 迁移 / 回填

覆盖扩展维度：错误路径与部分失败（重复执行）、兼容性（数据快照 · 旧数据口径）。

- **时间基准**（实现）：把 `now` 换成历史基准后，每个时间窗口是否仍有上下界？排序方向、相对文案、过期判断是否仍成立？
- **数据快照 · 复现语义**（文档）：读的是当前库还是当时的数据？没有快照时，「复现」只能叫「用历史时钟重跑」，文档是否说清？
- **数据快照 · 旧数据口径**（兼容性）：旧数据按新口径读会不会坏？
- **未来数据泄漏**（实现）：查询是否会把 `callTime` 之后产生的数据纳入（语义检索、冲突检测、图查询尤其容易）？
- **重复执行**（错误路径与部分失败）：写入是否带来源/批次标记，可识别、可清理、可回滚？
- **只读宣称**（文档）：注释说只读，实际是否更新印象值、统计、审计、缓存？
- **时区与单位**（实现）：DB 墙钟、JVM 时区、epoch 毫秒的换算是否只有一处真相？

## API / 库 / SDK

覆盖扩展维度：兼容性（参数契约 · 向后兼容）、并发与生命周期（共享状态）。

**本段是第 2 维「方法契约」的补充，不是覆盖**——第 2 维的扫描动作一条都不能省，扫完 playbook 不等于扫完第 2 维。

- **参数契约 · 清单与缺省**（方法契约）：第 2 维的参数清单、默认值、零值歧义。
- **参数契约 · 向后兼容**（兼容性）：旧调用方按旧默认值调用时，行为会不会变？
- **新增导出面的使用者**（过度设计）：有没有第二个使用者（第 7 维）。
- **错误语义是否可判别**（方法契约）：typed error / sentinel error，还是字符串比较。
- **文档示例**（文档）：示例是否可编译、可运行；示例用的默认值是否与实现一致。
- **共享状态**（并发与生命周期）：导出的指针字段、共享 map/slice、计数器是否允许多个调用方共用？非原子的读-改-写（`x++`）在并发下会丢更新并构成 data race。导出面若允许共享，要么用 atomic/锁保护，要么在 godoc 明确写「非并发安全，每次调用用独立实例」——**两种做法都对，但必须有一个，不能沉默**。
- **零值可用性**（方法契约）：导出类型是否零值可用？零值不可用时（必填字段、map/slice 未初始化），godoc 有没有写明「必须用构造函数」？两个包要一致——一个提供 `NewX()`、另一个靠零值，是调用方的困惑来源。
- **单位一致性**（方法契约）：同一个类型上，入口参数与出口返回值的单位是否一致（一个收「元」、一个返「分」）？把上游算出的总额直接传进去，会不会差一个数量级？
- **跨层形状**（方法契约）：根接口/抽象层声明的请求与结果类型，和具体后端（另一个存储、另一个适配器）实际用的类型，是同一个形状吗？有两个后端时，换后端要不要连带改调用方代码？这是契约裂缝，**能编译不等于形状一致**。
- **规模（该类型高发）**（规模与复杂度）：库的调用频率是关键——一个每秒调用十万次的方法里，一次线性查找就是问题；一个每天调用一次的批处理里则不是。调用频率能不能从调用方代码里读出来？

## 并发 / 服务 / 守护进程

覆盖扩展维度：并发与生命周期（共享状态与锁、启动顺序与关闭顺序、后台线程）、错误路径与部分失败（重试放大）、可观测性（失败可观测性）。

- **共享状态与锁**（并发与生命周期）：共享 map/slice/字段是否有保护；锁的粒度与顺序会不会死锁；channel/队列的关闭权归谁；线程池/goroutine 有没有退出路径；ctx 取消能不能传播到底层。
- **启动顺序与关闭顺序**（并发与生命周期）：shutdown hook、`System.exit`、异步任务是否被截断。
- **重试放大**（错误路径与部分失败）：重试、超时、限流是否叠加放大（重试 × 超时 × 并发）。
- **后台线程**（并发与生命周期）：后台线程是否在「单次运行」模式里仍被启动。
- **失败可观测性**（可观测性）：失败时有没有日志与退出码；后台线程的失败会不会被吞掉、能不能被告警发现；「服务已就绪 / 已停止」这类状态从哪看得到。

## 配置 / 部署 / 脚本

覆盖扩展维度：兼容性（环境差异与默认值）、可观测性（失败是否可观测）。

**本段是第 5 维「硬编码」的补充，不是覆盖**——第 5 维的扫描动作一条都不能省，尤其「协议固定值 vs 业务政策值」那一步。

- **环境差异与默认值**（兼容性）：环境差异、默认值、路径与端口换个环境是否还成立？
- **密钥与凭据**（安全）：密钥、凭据、文件权限、路径穿越。
- **失败是否可观测**（可观测性）：退出码、日志、健康检查、告警。
- **配置项是否真的被读取**（实现）：有没有「文档里写了、代码里没人读」的死配置。
