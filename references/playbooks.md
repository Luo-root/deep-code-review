# 按改动类型的追加检查

七维是通用面；下面这些改动类型有高频专属缺陷。先认类型，再追加对应清单——只对命中的类型展开，不要平铺到每次审查。

## 批处理 / Job / CLI

- **成功判定**：零写入、全部分片失败、全部跳过，是否仍返回 SUCCESS？「成功」是否等于「至少做成一件」？
- **游标 / 断点**：失败是否推进游标？跳过是否推进？重试入口是什么？`--reset` 会不会重复写？
- **幂等**：重跑同一输入会追加副本吗？有没有幂等键或批次标记？崩在「数据已写、进度未存」之间会怎样？
- **环境隔离**：会不会连生产库？会不会启动队列消费者、定时任务、HTTP 端口？有没有目标环境断言？
- **dry-run**：参数是否真的接线？只读是否覆盖所有写路径？启动日志里能否看出 dry-run 生效？
- **参数绑定**：`--key=value` 与 `--key value` 在当前框架里是否等价？裸 flag 是否真的映射到 `@Value` 的 key（`--dry-run` vs `memnet.replay.dry-run` 这种改名最容易断链）？命令行、环境变量、配置文件三个来源的优先级是否清楚？
- **退出码与摘要**：部分完成是否以 0 退出？「完成」文案是否与实际处理量一致？
- **分页**：只处理一页会不会被误认为全量？`limit` 与总量的关系是否可见？

命中这些项时，每条都要落到具体行；「文档这么写、代码没这么做」本身就是合法结论。

## 数据重放 / 迁移 / 回填

- **时间基准**：把 `now` 换成历史基准后，每个时间窗口是否仍有上下界？排序方向、相对文案、过期判断是否仍成立？
- **数据快照**：读的是当前库还是当时的数据？没有快照时，「复现」只能叫「用历史时钟重跑」，文档是否说清？
- **未来数据泄漏**：查询是否会把 `callTime` 之后产生的数据纳入（语义检索、冲突检测、图查询尤其容易）？
- **重复执行**：写入是否带来源/批次标记，可识别、可清理、可回滚？
- **只读宣称**：注释说只读，实际是否更新印象值、统计、审计、缓存？
- **时区与单位**：DB 墙钟、JVM 时区、epoch 毫秒的换算是否只有一处真相？

## API / 库 / SDK

- 参数契约（第 2 维）、默认值、零值歧义、向后兼容。
- 新增导出面是否有第二个使用者（第 7 维）。
- 错误语义是否可判别：typed error / sentinel error，还是字符串比较。
- 文档示例是否可编译、可运行；示例用的默认值是否与实现一致。

## 并发 / 服务 / 守护进程

- 共享状态、锁顺序、channel/队列的关闭权、线程池/goroutine 退出、ctx 取消传播。
- 启动顺序与关闭顺序：shutdown hook、`System.exit`、异步任务是否被截断。
- 重试、超时、限流是否叠加放大（重试 × 超时 × 并发）。
- 后台线程是否在「单次运行」模式里仍被启动。

## 配置 / 部署 / 脚本

- 环境差异、默认值、密钥与凭据、路径与端口、文件权限。
- 失败是否可观测：退出码、日志、健康检查、告警。
- 配置项是否真的被读取；有没有「文档里写了、代码里没人读」的死配置。
