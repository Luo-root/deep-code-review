## 口径说明（评分怎么算的）

按 `evals/rubric.md`：

- **命中**：对照 `ground-truth.md` 的 G1–G12，满分 12。命中且触发路径正确记 1；触发路径含糊记 0.5；漏报记 0。**只在「证据/边界说明」里点到、没有作为一条结论提出**的，记 0.5（C1 只算表达加分，不占命中）。
- **误报**：编造不存在的缺陷每条 −2；口味问题当问题报每条 −1；泛泛建议每条 −1；「不该报」清单里的候选每条 −1。
- **归类正确性**：逐条取平均，满分 12。级别与标准答案一致记 1；偏差一级记 0.5；偏差两级以上、或该拍板判成缺陷，记 0。**未报出的条目记 0**，所以这一项对漏报是二次惩罚——因此同时给出「按已报条目计」的辅助值。
- **证据强度**：每条 finding 定级（5 跑了测试/构造了最小复现；4 读了测试并确认覆盖或未覆盖；3 grep 了全部调用方；2 读了完整函数 + 相邻实现；1 只读了 diff），取该轮全部上报条目（含拍板项）的均值。声称强度高于实际做过的每条 −1；「已查过没问题」里没有验证方式的每条 −1。
- **表达质量**：逐条，满分 12。用大白话讲清机制且配了最小对照例子记 1；讲清机制没例子记 0.6；只有结论记 0.2；术语堆砌/行号当论据记 0。拍板类条目（G12）另加一条要求：给了「两条路 + 建议 + 要你定什么」才记 1。主动说清「哪块查过没问题」并给依据，对应 C1，额外 +0.5。
- **raw** = 命中 + 归类 + 证据均值 × 12 + 表达 − 误报扣分。

原始分数受标准答案缺陷影响（下一节），所以 raw 只在同口径内可比。

## 口径缺陷（本次评测暴露的标准答案问题）

这两条不是模型漏报，是标准答案自己站不住。修法已开票，**本文件的分数按修前的标准答案（v1）记录**，修后复算见下一节。

### G4：godoc 的「只读」承诺没有被兑现（判定有误）

标准答案写的是「文档承诺只读，实际写了 `c.Processed`（`:77`）与 `c.Stats.CheckedOut`（`:71`）」。但源码里那句承诺是有限定的：

```
// Checkout is read-only with respect to the order store: it never mutates
// orders and never writes back to the database.
```

限定语是「read-only **with respect to the order store**」——它承诺的是不动订单、不回写数据库。`c.Processed` 和 `c.Stats` 是 `Checkout` 自己的字段，不是订单存储，写它们不违反这句承诺。三轮里有两轮明确判定「该承诺成立」并给了推理（A：`checkout.go:67-78` 只读 `orders` 副本；B：逐行读 `Run` 确认无写操作）。把「有副作用」等同于「违反 read-only 承诺」是我当初写标准答案时的混淆。

B 轮提出的另一个角度更接近真实问题：承诺里提到的「订单存储 / 数据库」在这个模块里根本不存在，所以这条承诺没有对应对象——那是一条该进拍板的文档问题，不是「文档与实现矛盾」的 P1。

### G8：硬编码判定与 skill 自己的第 5 维细则冲突

标准答案要求把 `refundWindow = 24 * time.Hour` 当作硬编码报出。但 `references/dimensions.md` 第 5 维的「不算」条款写着：

> **不算**：真不变量（协议固定值、7 天），已命名、已注释、只有一个使用者。

同一维度的「算」条款又写着「它必须随环境/租户/调用方/**数据规模/版本**变化」——退款窗口会随业务口径变化，也就是随版本变化，按「算」条款应该报。同一节的两句话互相打架，B、C 两轮都明确按「不算」条款判了「硬编码：无发现」，并且把依据写出来了（已命名、已注释、单一使用者）。**模型没做错，是细则自相矛盾。**

需要人工拍板的是：退款窗口这类「业务政策值」到底算不算硬编码。我倾向要算——协议固定值（单位换算 100、HTTP 状态码）和业务政策值（退款窗口、账期）不是一回事，细则的括号里那个「7 天」例子恰好把业务政策值归进了「真不变量」，是根源。

## 方法论局限

- **样本与标准答案同一人写**：基线偏乐观，真实水平要打折看。这是本次评测最大的系统性偏差。
- **每种问法只跑 1 轮**：没有方差估计。同一 skill 两轮之间有波动是已知的（README 里写了），所以单轮差异小于 2 个百分点的结论不要当结论。

- **数值复算用的是 IEEE-754 等价推演**（.NET double 模拟 Go 的 `int64()` 截断与 `math.Round`），没有在被审目录里落 Go 探针（C 轮自己声明了这点）。Go 探针会给出同样的结论，但严格性差一点。
- **A 轮有一条依赖「该目录无 git 历史」这个前提**：五个文件全算「本次引入」。换一个真实的 PR，A 轮的行为会不同（届时要区分既有与新引入）。
- **没有做变异对照**：没有改坏代码去验证每条 finding 是否真能让测试变红，所以「finding 是真的」靠的是读码 + 数值复算，不是测试红。

## 结论先行

1. **新能力确实被用起来了**。rule-engine 两轮都把「依赖图按路径重复展开 → 指数膨胀」报成 P1 规模缺陷，都给了多档规模曲线（R1 命中 1/1）；两轮还都独立报了「依赖成环 → `fatal error: stack overflow` 整个进程死掉」（同样 P1）。**这是第 3 维成立条件（输入 → 错误结果）按定义抓不到的一类**——复杂度问题没有错误结果。
2. **误报两轮都是 0**。尤其 `DuplicateLines` 的 O(n²)：两轮都**明确驳回**了它（README 上限 200 行 → 19,900 次比较 ≈ 0.5 ms），并写进「已查过没问题」。这正是标准答案 v1 判错的那一条。

4. **R8（`ApplyChecked` 对任何非空规则集必然失败）两轮都漏**。C 轮甚至在「已查过没问题」里**明确肯定**了 `hasUnknownSKU` 的语义与 README 一致。语义分裂被识别了，**错误语义这一层没被追问**。

## 标准答案从 v1 到 v2 的校正

首轮（校正前 GT）两轮跑完后，标准答案自己被推翻了三处。**每处都有实测依据**。

| # | v1 | v2 | 依据 |
|---|---|---|---|
| 1 | R2 `DuplicateLines` 的 O(n²) 在「应当报出」，P2 | **移入「不该报」** | README 写明一次请求最多 200 个商品行。实测 200 行 → 19,900 次比较 ≈ **0.5 ms**。B 轮明确判定「O(C²) 本身不是问题」并给出实测数字。**原 GT 把「复杂度形状」当成了「规模后果」**——这正是要校准的东西 |

## 方法论局限

- **GT v2 有 4 条（R7–R10）是首轮输出反推补进来的**。每条都能从源码独立推导（不是「模型说了所以它对」），但**作者看过输出**这件事本身是偏差源。这四条的命中在这一轮带 ±0.5 的自证偏差，下一轮起应作为常规条目。
- **两个样本的 raw 不可比**：归一化因子 N 不同（25 vs 9）。跨样本只看维度占比。
- **tiny-shop 的 v4 基线跑在冻结提交 `7c1c4ea`**，本轮跑在 `dad4adc`；中间除了新能力还改了执行顺序。**轮间波动也很大**（B 命中 +5.5、C 命中 −2.5），单轮差异小于 3 个百分点的结论不要当结论。
- **每种问法只跑 1 轮**：没有方差估计。本轮四轮各只有一份样本。
- **本轮分数经过一次独立复算**（见上一节），四个 raw 相差 0–2.44，方向完全一致；但复算方在 11 处分歧上取了不同读法，**逐条对齐之前这些数字应视为区间**。
- **有一处覆盖声明失真**：tiny-shop B 轮的性能维度写「无无界缓存/无界分配」，与 GT 的 G18 相反——不构成编造缺陷、不扣误报分，但它是**假阴性**（与 v4 的 B 轮同款，说明这是该轮问法的稳定习惯）。
- **有一处结论计数与正文对不上**：tiny-shop C 轮结论写「P2 6」，正文只有 5 条 P2。**结论里的各级数量不可直接采信**，评分以正文条目为准。
- **没有做变异对照**：没改坏代码去验证每条 finding 是否真能让测试变红，「finding 是真的」靠读码 + 探针实测，不是测试红。
- **跨样本的绝对耗时不可换算**：rule-engine 的规模数字来自本机单次基准，外推到 README 的深度上限是按实测曲线递推，不是实测值。

## 结论

**自迭代没有提升审查能力；它提升的是「让合格的产出被正确判定为合格」。**

三条支撑：

1. **命中率两版持平。** rule-engine 两轮命中一模一样（16.0 / 18），tiny-shop 三轮 A 版还高 2.9 个百分点。没有任何一项显示 B 版更会找缺陷。

2. **归类方向不一致，不构成提升。** tiny-shop 是 B 版高 2.9 个百分点，rule-engine 是 A 版高 16.6 个百分点。这种量级的反向摆动说明它测的是噪声而非能力。

3. **raw 上 A 版反而更高**（758.24 对 748.0）。而 **raw 本身不能单看**：它约七成来自「证据均值 × N」，该均值的分母是各自报出的 finding 条目数——报得少则均值高。A 版 rule-b 报 20 条、raw 75.1；B 版同轮报 15 条、raw 65.2。**条目数与均值的这种耦合，让 raw 天然偏向「报得少而精」的一方。**

站得住的只有两条一致差异：

- **契约符合度**：B 版六轮全满分；A 版五轮全有扣分，且扣分理由完全相同——在六段骨架里插入了契约未定义的「建议修（P2/P3）」段。这不是模型乱写，是 A 版契约自身的空档：分级规则说 P2「建议修」，输出结构却没给这一段位置。
- **误报**：B 版六轮 0 条，A 版出现 1 条。

而这两条恰好解释了通过轮次的差距。A 版 rule-b 是最典型的一轮：**raw 75.1 是 12 轮里第二高，命中 88.9%、误报 0，却因为多写了一段契约里没有的段落被判「不通过」**。A 版 rule-c 同样（raw 68.9、契约 4.0/5）。那两轮审查质量没问题，是契约缺段让它们拿不到「通过」。

所以这次自迭代的真实价值是：**修掉了一个会让高质量报告被判无效的契约缺陷**。这是实打实的修复，但它属于「度量正确性」，不属于「能力提升」。

## 方法学局限

- **每种问法只跑 1 轮，无方差估计。** 12 轮里命中分的摆动幅度（rule-engine 上是 7.5–8.5 分，差 11 个百分点）大于两版之间的系统性差异。**任何小于 2 个百分点的差异都不应被当作结论**。
- **两版的产出由同一个模型、同一批 prompt 生成**，差异只来自契约。这与「换模型」的对比设计不同，结论不能外推。
- **A 版契约符合度按 5 项判、B 版按 6 项判**，是刻意的（按各自契约判才公平），但也意味着这一列不是同一个尺子量出来的绝对值，只能各自看「有没有扣分」。
- **rule-engine 的 GT 只有 9 条**，1 条就是 11 个百分点，该样本上的单轮差异尤其不可靠。
- **评分由单一评分 Agent 完成，未做双评一致性检验**；评分员列出的「需裁定」项（A 版 shop-d 的 G7 直接决定该轮通过与否）说明边缘判定的敏感性确实存在。

## 如果要真正验证「提升」

需要至少：同问法跑 3–5 轮取均值与区间；把「命中」按缺陷类型拆开（常识型 vs 判据型）分别统计；对每轮做双评一致性检验。现有 6 轮数据只够支撑上面那两条一致差异，不够支撑「能力提升」的结论。
