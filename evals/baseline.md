## 口径说明（评分怎么算的）

按 `evals/rubric.md`：

- **命中**：对照 `ground-truth.md` 的 G1–G12，满分 12。命中且触发路径正确记 1；触发路径含糊记 0.5；漏报记 0。**只在「证据/边界说明」里点到、没有作为一条结论提出**的，记 0.5（C1 只算表达加分，不占命中）。
- **误报**：编造不存在的缺陷每条 −2；口味问题当问题报每条 −1；泛泛建议每条 −1；「不该报」清单里的候选每条 −1。
- **归类正确性**：逐条取平均，满分 12。级别与标准答案一致记 1；偏差一级记 0.5；偏差两级以上、或该拍板判成缺陷，记 0。**未报出的条目记 0**，所以这一项对漏报是二次惩罚——因此同时给出「按已报条目计」的辅助值。
- **证据强度**：每条 finding 定级（5 跑了测试/构造了最小复现；4 读了测试并确认覆盖或未覆盖；3 grep 了全部调用方；2 读了完整函数 + 相邻实现；1 只读了 diff），取该轮全部上报条目（含拍板项）的均值。声称强度高于实际做过的每条 −1；「已查过没问题」里没有验证方式的每条 −1。
- **表达质量**：逐条，满分 12。用大白话讲清机制且配了最小对照例子记 1；讲清机制没例子记 0.6；只有结论记 0.2；术语堆砌/行号当论据记 0。拍板类条目（G12）另加一条要求：给了「两条路 + 建议 + 要你定什么」才记 1。主动说清「哪块查过没问题」并给依据，对应 C1，额外 +0.5。
- **raw** = 命中 + 归类 + 证据均值 × 12 + 表达 − 误报扣分。

原始分数受标准答案缺陷影响（下一节），所以 raw 只在同口径内可比。

## 口径缺陷（本次评测暴露的标准答案问题）

这两条不是模型漏报，是标准答案自己站不住。修法已开票，**本文件的分数按修前的标准答案（v1）记录**，修后复算见下一节。

### G4：godoc 的「只读」承诺没有被兑现（判定有误）

标准答案写的是「文档承诺只读，实际写了 `c.Processed`（`:77`）与 `c.Stats.CheckedOut`（`:71`）」。但源码里那句承诺是有限定的：

```
// Checkout is read-only with respect to the order store: it never mutates
// orders and never writes back to the database.
```

限定语是「read-only **with respect to the order store**」——它承诺的是不动订单、不回写数据库。`c.Processed` 和 `c.Stats` 是 `Checkout` 自己的字段，不是订单存储，写它们不违反这句承诺。三轮里有两轮明确判定「该承诺成立」并给了推理（A：`checkout.go:67-78` 只读 `orders` 副本；B：逐行读 `Run` 确认无写操作）。把「有副作用」等同于「违反 read-only 承诺」是我当初写标准答案时的混淆。

B 轮提出的另一个角度更接近真实问题：承诺里提到的「订单存储 / 数据库」在这个模块里根本不存在，所以这条承诺没有对应对象——那是一条该进拍板的文档问题，不是「文档与实现矛盾」的 P1。

### G8：硬编码判定与 skill 自己的第 5 维细则冲突

标准答案要求把 `refundWindow = 24 * time.Hour` 当作硬编码报出。但 `references/dimensions.md` 第 5 维的「不算」条款写着：

> **不算**：真不变量（协议固定值、7 天），已命名、已注释、只有一个使用者。

同一维度的「算」条款又写着「它必须随环境/租户/调用方/**数据规模/版本**变化」——退款窗口会随业务口径变化，也就是随版本变化，按「算」条款应该报。同一节的两句话互相打架，B、C 两轮都明确按「不算」条款判了「硬编码：无发现」，并且把依据写出来了（已命名、已注释、单一使用者）。**模型没做错，是细则自相矛盾。**

需要人工拍板的是：退款窗口这类「业务政策值」到底算不算硬编码。我倾向要算——协议固定值（单位换算 100、HTTP 状态码）和业务政策值（退款窗口、账期）不是一回事，细则的括号里那个「7 天」例子恰好把业务政策值归进了「真不变量」，是根源。

## 方法论局限

- **样本与标准答案同一人写**：基线偏乐观，真实水平要打折看。这是本次评测最大的系统性偏差。
- **每种问法只跑 1 轮**：没有方差估计。同一 skill 两轮之间有波动是已知的（README 里写了），所以单轮差异小于 2 个百分点的结论不要当结论。
- **快模式轮的 GT 覆盖天然不全**：G8 / G9 / G10 / G11 属设计面与测试面，快模式按契约本就不报。拿 A 轮的命中分去比全量轮是不公平的，上面的对比只应看「相对各自口径」。
- **数值复算用的是 IEEE-754 等价推演**（.NET double 模拟 Go 的 `int64()` 截断与 `math.Round`），没有在被审目录里落 Go 探针（C 轮自己声明了这点）。Go 探针会给出同样的结论，但严格性差一点。
- **A 轮有一条依赖「该目录无 git 历史」这个前提**：五个文件全算「本次引入」。换一个真实的 PR，A 轮的行为会不同（届时要区分既有与新引入）。
- **没有做变异对照**：没有改坏代码去验证每条 finding 是否真能让测试变红，所以「finding 是真的」靠的是读码 + 数值复算，不是测试红。

## 方法论局限（v4 轮补充）

- **样本与标准答案同一人写**：基线偏乐观，真实水平要打折看。
- **每种问法只跑 1 轮**：没有方差估计。单轮差异小于 2 个百分点的结论不要当结论。
- **快模式轮的 GT 覆盖天然不全**：G8–G11、G14–G25 多数属设计面与测试面，快模式按契约本就不报。拿 A 轮的命中分去比全量轮不公平。
- **B 轮有一条假阴性**：性能维度写「无…无界缓存」，与 GT 的 G18 相反。不构成编造缺陷、不扣误报分，但它是覆盖声明失真。
- **原始输出与评分表分离**：原始输出留在仓外（`scratchpads\dcr-eval-archive\`），版本控制里只有评分表——第三方可复算分数，但看不到原始报告全文。
- **数值复算以 Go 1.24.0 windows/amd64 实跑为主**；`int64(NaN)` 属平台相关的未定义转换，不同架构结果可能不同。
- **没有做变异对照**：没改坏代码去验证每条 finding 是否真能让测试变红，「finding 是真的」靠读码 + 探针实测，不是测试红。
