# evals —— 可复现的评测护栏

`deep-code-review` 是概率性的：同一份改动审两次，结论可能不一样。这没问题，但意味着
**「改完 skill 之后有没有变好」不能靠感觉**，得有护栏。

这个目录就是那个护栏。

## 组成

| 文件 | 作用 |
|---|---|
| `fixtures/tiny-shop/` | **自写**的最小样本仓库，刻意植入 25 个已知缺陷 + 1 个「应当确认没问题」的点 |
| `fixtures/rule-engine/` | 同上，专门测**算法复杂度**与**架构/设计语义**——tiny-shop 里没有这两种形态，测不出来 |
| `ground-truth.md` | tiny-shop 的标准答案：每个缺陷的位置、维度、级别、触发路径、可接受的变体，以及**不该报**的清单 |
| `ground-truth-rule-engine.md` | rule-engine 的标准答案（`R×` 编号，与 tiny-shop 的 `G×` 互不干扰），带 v1 → v2 的校正记录 |
| `rubric.md` | 评分表：命中 / 误报 / 归类正确性 / 证据强度 / 表达质量 |
| `runbook.md` | 怎么跑、跑哪几种问法、什么时候必须跑 |
| `baseline.md` | 历次评测的基线分数，**追加**不覆盖；每轮都记着当时的标准答案口径 |

样本是**自己写的**，不来自任何第三方仓库，所以没有许可问题，也不会把别人的代码带进本仓库。

## 两个样本各测什么

| 样本 | 测的面 | 跑哪几轮 |
|---|---|---|
| `tiny-shop` | 契约、文档、错误路径、并发、兼容性——**通用面** | A + B + C |
| `rule-engine` | 算法复杂度、语义分裂、跨层形状——**新能力面** | B + C |

**为什么必须是两个样本**：tiny-shop 是 184 行的结算模块，里面没有指数级回溯，也没有分裂成两条路径的动作。
只跑它就分不清「新能力生效了」和「模型本来就会」；两个样本分开跑、分数分开记，才能同时回答这两问。

样本规模是 `evals/` 里唯一的口径，下面这张表是**唯一真相源**——其它文件描述样本大小时必须用这两个数字，
`tools/lint-consistency.mjs` 会拿它们跟实测行数、以及跟各文件的写法逐项比对：

| 样本 | Go 源码行数 |
|---|---|
| `fixtures/tiny-shop/` | 184 行 |
| `fixtures/rule-engine/` | 377 行 |

## 样本为什么长这样

### tiny-shop —— 测「能不能找到 bug」与「会不会乱报」

它刻意覆盖了几类「模型最容易犯错」的地方：

- 一个**指针字段没有构造函数** → 零值就 panic（实现维度）
- 一个**参数被完全忽略**（`timeout`）和一个**字段被完全忽略**（`Code`）→ 契约维度
- **一个承诺提到了根本不存在的层**（文档说「不回写数据库」，但模块里没有数据库）→ 文档维度
- **批次中途失败会丢计数** → 错误路径维度
- **同一逻辑写在两个包里且已经漂移**（截断 vs 四舍五入）→ 重复维度
- **同一个错误码有两个错误值** → 兼容性维度
- **一个没有使用者的接口** → 过度设计维度
- **测试永远手工初始化那个会 panic 的字段** → 测试盲区维度
- **一个该进「需要你拍板」而不是判成 bug 的业务口径** → 判定纪律维度
- **一块确实写对了的并发代码** → 用来测「会不会凭空编造竞态」

最后两条是这个样本最值钱的地方：它们测的不是「能不能找到 bug」，而是**「会不会乱报」**——
那才是让作者不再看报告的原因。

### rule-engine —— 测「能不能看出设计本身不合理」

- **依赖图按路径重复展开**（没有已访问集合）→ 规模与复杂度维度
- **每层深拷贝完整依赖链** → 规模与复杂度 / 过度设计维度
- **每次查折扣都重建整张索引表，且在热路径的循环里** → 规模与复杂度维度
- **同一个动作两条路径行为不一致**（一个回写购物车一个不回，一个跳过一个报错）→ 语义分裂维度
- **抽象层与后端层类型不是一个形状**（换后端要改调用代码）→ 跨层形状维度
- **一个承诺没有落地**（godoc 说「规则集在构造时固定」，实现却直接持有调用方切片）→ 文档承诺维度
- **一个在文档上限内根本不成立的复杂度形状**（O(n²)，但上限 200 行实测 0.5 ms）→ 测「会不会把形状当后果」

> **首轮评测校准过 tiny-shop 那条**：原本这里写的是「文档承诺只读但实现写了状态」，标准答案也据此设了一条 P1。
> 但源码那句承诺有限定语「read-only *with respect to the order store*」，写 `Checkout` 自己的计数器不违反它，
> 而且模块里根本没有数据库可供违反。**是标准答案写错了，不是模型漏报**——详见 `baseline.md` 的「口径缺陷」一节。
>
> **rule-engine 的标准答案也校准过 3 处**：O(n²) 那条从「应当报出」移到「不该报」（量级不够），
> 索引重建那条级别 P2 → P1（README 上限下单请求 877 ms），语义分裂那条从缺陷改成拍板（godoc 已承认差异）
> 并拆出三条新条目。依据与逐条对照见 `baseline.md`。

## 跑一次

见 `runbook.md`。

CI **不跑**评测：评测需要调用模型，成本高、结果不确定，也不适合放进阻断式流水线。
CI 只做静态校验（换行符 + skill lint）。评测是人工触发的纪律。

## 现状

这套护栏随 issue #11 引入，已经跑过多轮，分数与口径缺陷见 `baseline.md`。

**当前有效口径是 pass-6**（冻结提交 `4c30903`）：6 轮实测，**只有 2 轮通过放行门槛**
（rule-b / rule-c，都是 rule-engine 样本）；tiny-shop 四轮的命中率稳定停在 63% 左右，距 70% 门槛仍有缺口。
历史归档 pass-3（`5e7ed91`）、pass-4（`bcdad90`）对应的是旧契约，**不能与 pass-6 比**。
基线状态见 `baseline.md` 顶部的「基线状态」一节。

**pass-6 同时做了一组 A/B 对照**：用同一批样本、同一套 rubric，分别评估自迭代前（`28e3b4c`）与
自迭代后（`4c30903`）的契约产出。结论是**输出规范性提升明显（契约符合度 6 轮全满分 vs 5 轮全有扣分、
误报 0 对 1）、判定正确性提升（同样的审查结果在旧契约下会因缺段被判无效），但没有可测的审查能力提升**
（命中率两版持平，rule-engine 两轮命中完全相同）。逐轮数据与方法学局限见 `baseline.md` 文末「pass-6 · A/B 对照」。

口径也换过：pass-4 换了 `rubric.md` 的第 6 维「输出契约符合度」、GT 的「允许级别集合」与
「D 轮归属表」、以及快模式轮的判分口径——**pass-4 的分数与 pass-3 不可比**，它是新口径下的第一个基线。

后续每次改动都和基线比。**注意口径**：改了 `ground-truth.md` / `ground-truth-rule-engine.md` 或 `rubric.md` 之后，
旧分数与新分数不可比——必须重跑一轮，把新一节追加到 `baseline.md`，不要覆盖旧记录。
**跨样本的 raw 也不可比**（归一化因子 N = 该样本的 GT 条目数，25 vs 9），只能比维度占比。
