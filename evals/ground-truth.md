## 不该报

| 候选 | 为什么不报 |
|---|---|
| 两个包都叫 `package shop`、一个文件里放多个类型 | 命名与分包口味，`SKILL.md` 的不报清单第一条。两个包同名时，同一文件里一起 import 而不起别名，编译器**会**报 `shop redeclared in this block`——但起个别名就能解开，编译器会拦住，不会有错误代码上线 → 仍不算缺陷；要提只能进「需要你拍板」 |
| `checkout.go:60-61` 承诺「never mutates orders and never writes back to the database」但写了 `c.Processed` / `c.Stats` | **该承诺有限定语**「read-only *with respect to the order store*」，写 `Checkout` 自己的计数器不违反它；模块里也没有数据库可供违反。**不算缺陷**（G4 改后指的是另一个问题：承诺本身没有对应对象） |
| `refundWindow` 没导出 | 未导出常量不构成公开契约问题；过度设计维度里「公开契约」是除外项 |

## 计分要点

- **同一根因只算一次**：例如「折扣能力整体没接线」如果被拆成 G3 / G9 / G25 三条报出来，按出现顺序取靠前的一条计分，其余不重复加分。
- **归类正确性单独计分**：把 G12 报成 P0/P1 的，即使结论方向对也要扣分——它测的是「先判设计使然还是缺陷」这条纪律。
- **C1 的正向确认单独计分**：主动说清「这块没问题」比不报错更有价值；只在覆盖表里写「并发：无」也算，但带依据的更好。
- **G13 可以判成 bug，也可以判成拍板**：这个模块没有任何调用方，「该不该有退款窗口」本身就是业务问题。判成拍板并给出两条路 + 建议的，**同样算命中**；判成 P1 缺陷的也算命中。但把它说成「已经确认的 bug」而不谈业务前提的，归类扣分。
- **G8 修过口径**：现在 `refundWindow` 属「业务政策值」，按 `references/dimensions.md` 第 5 维的新细则**应该报**。仍然按「真不变量」判为不报的，不算漏报——那一版细则确实有歧义，但复评时以新细则为准。
- **「包名」这条的理由修过**：原文写「import 别名是 Go 的正常机制、编译器不报错」，实测是错的——两个同名包在同一文件里一起 import 而不起别名，编译器会报 `shop redeclared in this block`。**处置规则没变**（仍然只能进「需要你拍板」，进「必须修/建议修」算误报），所以修正前后的口径对同一份输出给分相同。

## 允许级别集合（契约允许多级时）

下列条目的级别在契约下**不止一个合法答案**——GT 表里的级别是首选答案，不是唯一答案。
落在集合内即算归类正确（rubric「归类正确性」记 1），与首选级别不同也不扣分。

| 条目 | 允许级别 | 理由 |
|---|---|---|
| G6 | P1 / P2 | 契约的 P1 是「在可预测的真实输入下出错」，P2 是「持续制造维护成本」。两条换算路径在带小数的金额上真的会差 1 分（P1），而它同时也是两个真相源（P2）——两级都成立 |
| G13 | 拍板 / P1 / P2 | GT 本就允许判成 bug 或拍板；判成 bug 时级别按 P1 / P2 都成立（窗口永远关不上是 P1，语义错是 P2）。**但「没谈业务前提就说成已确认的 bug」仍然按细则四的第 3 条记 0.5** |
